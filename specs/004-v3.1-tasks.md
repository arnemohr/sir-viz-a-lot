# 004 v3.1 — task breakdown

Companion task spec for [`004-v3.1.md`](004-v3.1.md). Each task below is
sized for a single PR; Sonnet implements, Opus reviews against the
acceptance checkboxes.

## Operating model

- **Pick one task at a time.** Read the source section it references in
  `004-v3.1.md` and the corresponding entry in `specs/roadmap.md` before
  starting.
- **Commit message format:** `004-V31.<workstream>.<task>: <title>` —
  e.g. `004-V31.1.1: fix static-value modulator round-trip`.
- **Branching:** one branch per task; merge straight to `main` once Opus
  signs off.
- **Pre-commit hook** (`.githooks/pre-commit`, wired by `make setup`)
  runs rustfmt on staged files + `cargo check`. Heavier checks live in
  `make ci`; run that before opening a PR.
- **Tests:** every task ships with new or updated tests. v3.1 is
  cleanup + small adds — there is no "we'll add tests later" exception.
- **Read the right CLAUDE.md.** Tasks touching `src/project/` must read
  `src/project/CLAUDE.md` first (Mutation Reverse-storage rules,
  snapshot invariants). Tasks touching `src/render/` must read
  `src/render/CLAUDE.md` first (GPU lifecycle, panic_restore,
  build-time WGSL validation).
- **Don't bundle.** If a task tempts you to also fix something nearby,
  resist — that "something nearby" probably already has its own task ID
  below.

## Task ID conventions

- IDs are flat-numbered within nine workstreams plus a release-housekeeping
  workstream:
  - W1 — Deferred audit findings
  - W2 — Schema v6 portable monitor
  - W3 — Reverse-storage refactor
  - W4 — Native macOS menu bar
  - W5 — Demo content
  - W6 — Layer solo / mute
  - W7 — BPM HUD + quantize
  - W8 — Output preview thumbnail
  - W9 — Audio bands strip
  - W10 — Release housekeeping
- Pre-existing T-numbers from spec 003 (e.g. T1.36, T4.19) are kept in
  the **Source** field of each task, so the audit trail back to the
  original work survives.

### V31.1.1 — fix static-value modulator round-trip

**Source:** `004-v3.1.md` "Deferred audit findings" → T1.36
**Type:** bug fix
**Depends on:** none
**Files:** `src/modulators/`, `src/project/` (snapshot path), proptest
fixtures.

**What:** static-value modulators lose precision (or value) across a
save → load round-trip. Reproduce, then fix.

**Steps:**
1. Locate the static-value modulator variant (likely
   `Modulator::Static(f32)` or similar in `src/modulators/`).
2. Write a proptest that round-trips a project containing a static
   modulator at arbitrary `f32` values through save → load.
3. Confirm the test fails on `main`.
4. Fix — likely a serde representation or a snapshot-restore path
   issue. Read `src/project/CLAUDE.md` first (`restore_scene` ≠
   `restore`).
5. Test passes; existing modulator tests still pass.

**Tests:**
- New proptest in `src/project/tests` (or wherever Mutation proptests
  live) covering static modulator round-trip across the full `f32`
  range, including edge cases (`NaN`, `±∞`, subnormals).

**Acceptance:**
- [ ] Proptest reproduces the bug on `main` (commit the failing test
      first, then the fix).
- [ ] Fix lands in the same PR; test passes.
- [ ] No regression in existing modulator tests.
- [ ] `make ci` clean.

**Out of scope:** other modulator types (sine, tri, noise, BPM, audio)
unless the same root cause affects them — flag separately if so.

## Workstream 3 — Compile-time Reverse-storage refactor

The cleanest place to ship this is *before* W2 and W6 add new Mutation
variants — the trait then forces both new sets to declare their reverse
storage at the type level.

### V31.3.1 — design + pattern: type-level `ReverseStorage`

**Source:** `004-v3.1.md` "Compile-time Reverse-storage refactor" →
T1.14 follow-on
**Type:** design + refactor
**Depends on:** none
**Files:** `src/project/command.rs`, `src/project/CLAUDE.md` (update
to reflect the new convention), possibly a new derive-macro crate
(see step 2).

**What:** replace the per-variant Reverse-storage convention (today's
hand-written `match` arms in `Mutation::reverse(self)`, see
`src/project/command.rs:480` onward) with a type-level guarantee.

**Hard constraint to preserve:** adding a new `Mutation` variant must
fail to compile unless its Reverse-storage is declared. The existing
`Mutation` is one enum (`#[non_exhaustive] pub enum Mutation { … }`),
so a single `trait ReverseStorage` with an associated type does *not*
naturally apply per-variant. Two viable patterns — pick one in this
PR:

  - **(A) Enum-of-structs.** Each variant becomes its own struct
    (`SetGamma { new, old }`, `SetBrightness { new, old }`, …) that
    implements `ReverseStorage`; `Mutation` becomes a thin enum
    wrapping the structs. Compile-time guarantee comes from the
    `match` in `Mutation::apply` requiring an `impl` for every wrapped
    struct.
  - **(B) Derive macro.** Keep `Mutation` as today's enum but add
    `#[derive(ReverseStorage)]` (new proc-macro crate) that generates
    the per-variant capture/apply. Compile-time guarantee comes from
    the macro's exhaustiveness check.

**Steps:**
1. Read `src/project/CLAUDE.md` to understand the three current
   Reverse-storage rules (whole-enum, effects-vec, snapshot).
2. Pick pattern (A) or (B) with a one-paragraph rationale committed
   into the PR description (and into `src/project/CLAUDE.md` as the
   new convention). Default recommendation: **(A) enum-of-structs** —
   no new build-time dep, easier for Sonnet to replicate variant by
   variant in V31.3.2, and the `#[non_exhaustive]` attribute already
   in place forces match exhaustiveness at the wrapper level.
3. Define the trait. Sketch (signature should match the existing
   `apply`/`reverse` flow at `src/project/command.rs:480`):
   ```rust
   trait ReverseStorage {
       fn apply(self, project: &mut Project) -> Self;
       // Returning Self gives the reverse for free — same shape as
       // today's Mutation::reverse, just per-variant instead of
       // hand-matched.
   }
   ```
4. Implement the chosen pattern for **one** existing Mutation variant
   (suggested: `SetGamma`, the simplest) — don't migrate the whole
   enum yet (that's V31.3.2).
5. Add a unit test that confirms the migrated variant behaves
   identically to the pre-refactor `Mutation::reverse` path on a
   round-trip.
6. Update `src/project/CLAUDE.md` to document the new convention and
   mark the three per-variant rules as superseded (rules are now
   enforced by the trait, not by hand).

**Tests:**
- Unit test on the migrated variant proving identity with the prior
  behaviour (apply → reverse → apply round-trips byte-equal on the
  project).

**Acceptance:**
- [ ] Pattern (A) or (B) chosen and rationale documented.
- [ ] Trait defined with clear semantics.
- [ ] One variant migrated as a pattern (PR shows the diff Sonnet will
      replicate across the rest in V31.3.2).
- [ ] `src/project/CLAUDE.md` updated.
- [ ] No runtime behaviour change.

**Out of scope:** migrating all variants (V31.3.2).

### V31.7.3 — quantize gate on cue firing

**Source:** `004-v3.1.md` → N3 partial / acceptance criterion

**Depends on:** V31.7.1, V31.7.2

**What:** when quantize is set to N bars, a cue-fire (key `1`–`9` or

the snapshot.

**Steps:**

   intended cue and arm; on the next bar-boundary tick from the BPM
   modulator, fire.

   from `roadmap.md` §F (idle / armed / live) — pending-quantize
   counts as armed-next.

**Tests:**

  4 bars, fires a cue, advances BPM clock, asserts fire timing is
  within ±1 frame of the bar boundary.
- Confirm quantize = off is bit-identical to v3 cue behaviour.

**Acceptance:**
- [ ] Quantize 1/2/4/8 each delays cue fire to the right boundary
      within ±1 frame.
- [ ] Quantize off preserves v3 behaviour exactly.
- [ ] Cue tile shows armed state during the wait.

**Out of scope:** chain-of-cues, follow-on cues, timecode triggers —
